# Kavrune engineering standards

These permanent rules adapt the supplied Global Desktop Application Development Standards to Kavrune's offline Linux storage use case. They apply to features, UI, data, packaging and release claims. [STANDARDS_ASSESSMENT.md](docs/STANDARDS_ASSESSMENT.md) maps all 25 checklist sections and the 24 release criteria to evidence and remaining work.

1. Every visible control must perform its named action. Use accurate text, useful empty/error states and real progress; keep technical diagnostics secondary except where a device path/serial is needed to prevent erasing the wrong drive.
2. Keep presentation, core I/O and Linux integration separate. Shared contracts belong in headers; business logic must be testable without presenting a window or opening a physical drive. Prefer focused changes over new architectural layers with no use case.
3. Run as the ordinary user. Use only documented UDisks/Polkit authorization; never bypass target identity, source pinning, system ancestry checks, confirmation or mandatory readback verification. Fail closed when identity/topology is unknown.
4. Treat files, device metadata, filenames, logs and filesystem changes as untrusted. Bound parsing, memory, diagnostics and temporary files. Refuse unsafe links, unexpected file types and overwrite attempts. Preserve a replacement file during failed-operation cleanup.
5. Keep local-file operations functional without internet. Embed necessary UI/legal content. Do not add accounts, cloud APIs, remote assets, telemetry, automatic uploads or download/update services without a separately approved product requirement and matching privacy/security design.
6. Users control their local images, backups and diagnostics. Explain where data is stored, retention, export, clearing and uninstall behavior. Do not call permissions encryption or deletion secure erasure. Update [PRIVACY.md](PRIVACY.md) whenever storage or sharing behavior changes.
7. Use native, accessible controls and dialogs with persistent labels, keyboard access and visible feedback. Respect system theme, fonts, scaling and reduced motion. Test compact layouts and all visible states; do not claim screen-reader or contrast certification without measurement.
8. Keep blocking I/O off the GUI thread. Bound background work; show an elapsed heartbeat while a drive is saving. Never infer completion from bytes submitted or guess hardware progress/remaining time. Cancel safely and release lifecycle inhibitors on every completion/failure path.
9. Use UTF-8 and human-readable sizes/times. Keep machine JSON locale-independent. Externalize GUI strings, allow expansion and record unsupported translations honestly. Safety identity strings remain exact where required for confirmation.
10. Do not persist destructive target selection, authorization, passwords or automatic job resumption. Add preferences only when they have a real effect, validated versioned persistence and safe reset behavior. Respect OS-managed preferences where no app override is needed.
11. Use the CMake version as the product version. Keep identity, notices, metadata, documentation, artifacts and diagnostic reports consistent. Preserve MIT and dependency obligations; no forced consent gate, invented operator identity or broad legal/compliance assurances.
12. Every important failure mode needs an appropriate regression or a recorded manual acceptance case. Test source/target mutation, malformed metadata, cancellation, errors, no-clobber output, privacy controls and missing services with disposable fixtures.
13. Validate the packaged binary and embedded resources, not only source builds. Check hardening, runtime search paths, package permissions, current documents, offline operations and artifact integrity. Extraction tests are not package-manager installation tests; local smoke measurements are not baseline hardware qualification.
14. Updates are manual through the user's package manager/trusted distribution process. Never start a destructive update or installation in the background. Before a supported release, require authenticated provenance, clean installation/upgrade/removal tests, current dependency review and repeatable artifact creation.
15. Publish a candid result: implemented, verified, pending, not applicable, and why. A test pass is bounded evidence. Production readiness additionally needs the full hardware/firmware, accessibility, distribution, security, legal and support acceptance matrix in [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md).

For each change: inspect the implementation and rules; identify trust boundaries/failures; implement; add meaningful checks; run them; inspect relevant UI; update actual policies/status; report limitations. Use [TEST_PLAN.md](TEST_PLAN.md) and [PRIVACY_AND_LEGAL.md](PRIVACY_AND_LEGAL.md). Public standards such as NIST SSDF and native accessibility guidance inform design; no certification is claimed.
